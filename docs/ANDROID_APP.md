Module: `mobile/android/app` — a real Android application (Compose, Material 3).

## Build and run

```bash
cd mobile/android
export JAVA_HOME=/opt/homebrew/opt/openjdk@17   # any JDK 17
echo "sdk.dir=$HOME/Library/Android/sdk" > local.properties   # git-ignored
./gradlew :app:testDebugUnitTest   # JVM unit tests (JUnit 5)
./gradlew :app:lintDebug
./gradlew :app:assembleDebug       # app/build/outputs/apk/debug/app-debug.apk
./gradlew :app:assembleRelease     # R8 + shrink, unsigned: app/build/outputs/apk/release/
./gradlew :app:installDebug        # emulator/device
```

Debug talks to `http://10.0.2.2:8080` (the host's backend from the emulator);
cleartext is allowed only to `10.0.2.2`, `localhost` and `127.0.0.1`, and only in
the debug network security config. Release uses `https://api.kerno.mx`
(placeholder), HTTPS only, R8 minify + resource shrinking, **unsigned**: no
signing keys live in the repo (debug uses the default debug keystore).

Log in with a phone number; with the backend in `DEV_MODE` the OTP code is
printed in the server log.

CI (`.github/workflows/ci.yml`, job `kotlin`) runs
`:app:testDebugUnitTest :app:lintDebug :app:assembleDebug :app:assembleRelease`
(platform `android-36`, build-tools 35.0.0); `gradle/actions/setup-gradle`
also validates the wrapper jar against Gradle's published checksums.

## Architecture

- `MainActivity` → `KernoApp` (Compose). FLAG_SECURE is set app-wide through
  `WindowSecurityGuard` (Android adapters in `ui/security/AndroidWindowSecurity.kt`).
- Manual DI: `AppContainer` (one per process, owned by `KernoApplication`).
- Navigation (navigation-compose): no session → login; session without a
  merchant and several memberships → merchant picker; otherwise bottom bar
  *Inicio* (balances), *Cobrar*, *Ventas* (list + detail with refunds),
  *Perfil* (profile, CLABE, *Facturas*, *Sellos digitales (CSD)* for owners,
  switch merchant, logout). The merchant app is
  keyed on user + merchant, so switching tenant rebuilds every ViewModel.
- ViewModels are `androidx.lifecycle.ViewModel`s with injected APIs and an IO
  dispatcher, unit-tested with fakes (`src/test`). API clients are blocking
  OkHttp + kotlinx.serialization, called on the IO dispatcher.
- Money is `Long` cents end to end (`MoneyFormatter` formats without floats);
  the keypad reuses `PosTerminalViewModel`, the QR reuses `CodiQrGenerator`.

### Auth (`auth/`, contract in `docs/AUTH.md`)

- `HttpAuthApi`: `/api/v1/auth/otp/request`, `/otp/verify`, `/refresh`, `/logout`
  over a client **without** the bearer interceptor.
- `SessionManager`: persists the token pair, refreshes **single-flight**
  (concurrent 401s rotate the refresh token once; a second use would trip the
  backend's reuse detection and revoke the family). Only a definitive
  rejection on `/refresh` ends the session (`401 REFRESH_TOKEN_INVALID` /
  `REFRESH_TOKEN_REUSED`, or an `invalid_grant` code); network errors, `429`,
  `403` and 5xx keep it, so a bad connection or a rate limit never logs the
  merchant out. Logout revokes the family server-side and wipes the device.
  `TokenPair.toString()` / `StoredSession.toString()` never print tokens.
- `AuthInterceptor` adds `Authorization: Bearer` and refreshes proactively 30 s
  before expiry; `TokenAuthenticator` refreshes once on 401 and retries once.
  This also covers the backend's `iss`/`aud` check (MVP-31): an access token
  minted before that deploy, or for another audience, gets the gate's `401
  {"error":"unauthorized"}`; refresh tokens are opaque, so the one refresh
  returns a valid token and the request is retried (verified against the
  captured 401 in `contract/AuthContractTest`; no app change was needed).
- Storage: `EncryptedTokenStore` keeps only AES-256-GCM ciphertext in private
  SharedPreferences; the key is generated in the Android Keystore
  (`AndroidKeystoreKeys`). Interfaces (`TokenStore`, `SecretCipher`,
  `KeyValueStore`) make it JVM-testable. Undecryptable blobs are dropped (user
  logs in again). Backups/device transfer exclude app data.

### Charge (card contract in `docs/ACQUIRER_INTEGRATION.md` §2)

- **Tarjeta (Tap)**: `POST /api/v1/card-payments/intents {amount_cents, currency:"MXN"}`
  with an `Idempotency-Key` that is stable per attempt (no `is_persona_moral`:
  the backend derives it) → `TapToPayProvider.collect(intent)` starts the
  processor SDK with `provider_payment_id` + `client_secret` (never logged) →
  poll `GET /api/v1/card-payments/{id}` until `final:true` (backoff 0.5 s ×1.5,
  capped at 3 s, 60 s timeout measured on a monotonic clock so slow GETs
  count → "en confirmación", check *Ventas*). `final` is false only for
  `CREATED`/`AUTHORIZED`. The SDK only starts for a `CREATED` intent with a
  `client_secret`: a replay of an already tapped intent (no secret) goes
  straight to polling and is never canceled by the app. The SDK
  result is informative only; the screen follows the backend status:
  `CAPTURED` (or later refund/chargeback states) = approved, `DECLINED` shows
  the `decline_code`, `CANCELED` back to the keypad.
- Retries (`isUnknownOutcome`, shared with refunds): no response, an
  unparsable one, or any 5xx except `ACQUIRER_REJECTED` /
  `ACQUIRER_NOT_CONFIGURED` keeps the key (e.g. `502 ACQUIRER_UNAVAILABLE`,
  `500 CARD_PAYMENT_STORE_FAILED` after the row was stored, a proxy `504`),
  so the retry replays the same intent. Any 4xx (`409 IDEMPOTENCY_KEY_REUSED`,
  `403 MERCHANT_NOT_APPROVED`...), a definitive rejection, a decline or a
  cancel drops it and the next attempt is a new intent. Changing the amount
  also drops it (the backend would answer `IDEMPOTENCY_KEY_REUSED`).
- Merchant gate: `403 MERCHANT_NOT_APPROVED` (onboarding not approved) links
  to the KYB screen; `403 MERCHANT_BLOCKED` (blocked by an operator) shows
  its own message. Exact codes, no substring matching.
- *Cancelar cobro* while waiting for the card stops the SDK and calls
  `POST /api/v1/card-payments/{id}/cancel` (`200` canceled / `202` requested;
  the webhook moves the status). An SDK failure also cancels the intent.
- **SPEI QR**: reads the merchant's `clabe` (`GET /api/v1/merchants/{id}`),
  draws a QR with `{v, type:"SPEI", clabe, beneficiary, amount_cents, reference}`
  (7-digit numeric reference, 15 min expiry) plus the CLABE and reference as text.
  This is a Kerno payload, not CoDi/DiMo; payment is credited when the STP
  abono arrives.

### Sales

`GET /api/v1/merchants/{id}/sales?limit=50&before=<cursor>` →
`{"items":[{id, kind:"card"|"spei"|"codi", status, amount_cents, created_at, card_payment_id?,
invoice_id, invoice_kind, invoice_status, credit_notes?}], "next_cursor"}` (invoice fields since
the backend Lote K, explicit `null` when not invoiced; see `docs/MONEY_FLOWS.md`).
`invoice_*` is the **active** invoice holding the sale (`PENDING` / `STAMPED` /
`CANCEL_REQUESTED`; a `FAILED` or canceled one frees it). The list marks each
sale (`SaleInvoiceMark`): *Facturando* (individual `PENDING`), *Facturada*,
*Factura en cancelación* (`CANCEL_REQUESTED`) or *En factura global*
(`invoice_kind GLOBAL`). Those sales are not invoiceable: their checkbox and
*Facturar* in the detail are disabled beforehand. The detail links to the
invoice (*Ver factura* / *Ver factura global*) and lists its `credit_notes`
(`{invoice_id, status, uuid?, related_invoice_id, total_cents}`, Long cents),
each opening the credit note in *Facturas*.
Statuses: card = `card_payments.status`; SPEI and CoDi rows come from
`merchant_sales`, which only holds credited money (`RECEIVED` / `CONFIRMED`,
both shown as approved). A card intent that was never tapped stays `CREATED`
(shown as pending).
The list asks for the next page (`before=next_cursor`) when its end is
reached; `null` = last page; duplicates across pages are dropped; *Actualizar*
starts over from the first page.

### Refunds and sale detail (`docs/ACQUIRER_INTEGRATION.md` §4)

The detail of a card sale reads `GET /api/v1/card-payments/{card_payment_id}`
and shows captured / refunded / chargeback amounts, the settlement split
(fee, tax set-aside, net) and the decline code. Owners (session role
`owner`; hidden for cashiers/operators, the backend enforces it too) can
refund the whole refundable remainder (`{}`) or a typed amount
(`MoneyParser`, Long cents, ≤ 2 decimals, ≤ refundable), after a
confirmation dialog: `POST /api/v1/card-payments/{id}/refunds` with an
`Idempotency-Key` stable per attempt and amount (kept while the outcome is
unknown, same rule as intents: e.g. `500 CARD_REFUND_STORE_FAILED` can follow
a refund the processor accepted; dropped on 4xx and `502 ACQUIRER_REJECTED`,
whose body also carries the `FAILED` refund). Cashiers get `403
ROLE_FORBIDDEN` unless the backend sets `ALLOW_CASHIER_REFUNDS`. The `202 PENDING`
request is shown as such; the money moves when the processor's
`payment.refunded` arrives (in debug the DEV simulator plays it with
`{"outcome":"refund","refund_id"}`). Statuses `PARTIALLY_REFUNDED`,
`REFUNDED`, `CHARGEBACK` (amount debited from the available balance) and
`CHARGEBACK_REVERSED` have their own labels.

### Sale receipt (`payments/SalesApi.kt`, contract in `docs/CFDI.md` § Comprobante de venta)

The detail re-reads the sale with `GET /api/v1/merchants/{id}/sales/{sale_id}`
(the list's copy is shown meanwhile and kept if that call fails; after a
process death the detail loads from it alone). A confirmed sale carries
`receipt_url` + `receipt_expires_at` and, for card sales, `card {brand,
masked_pan "**** 1234", auth_code}` (an untapped intent sends an empty `card`
object; SPEI/CoDi send none). PCI: `SaleCard.sanitized()` keeps only the last
4 digits whatever the backend sends, and `toString()` prints brand + last 4
only; nothing is persisted. With `RECEIPT_BASE_URL` unset the backend sends
a relative `/r/…`: `HttpSalesApi` resolves it against the API base URL so the
shared link always works.
- *Compartir comprobante*: plain-text `ACTION_SEND` share sheet with the
  amount and the public link (WhatsApp, SMS, email…). No tenant data.
- *Enviar comprobante* (owner and cashier; hidden for operators, the backend
  enforces `requireRole(owner, cashier)` too): optional email and Mexican
  mobile (10 digits → E.164 `+52…`, same rule as login) → `POST …/sales/
  {sale_id}/receipt {"email"?,"phone"?}` (empty fields are not sent) →
  `200 {receipt_url, expires_at, sent:{email,sms}}` shown per channel. No
  Idempotency-Key (the backend just sends again; the button is disabled while
  sending). Errors: `502` with the same body (`sent` says which channel
  failed; inputs kept for *Reintentar*), `422 RECEIPT_DESTINATION_INVALID
  {fields}`, `409 SALE_NOT_CONFIRMED`, `403 ROLE_FORBIDDEN`, `503
  RECEIPTS_NOT_CONFIGURED`.

### Merchant picker

The token pair's `memberships` (`merchant_id`, `role`, `merchant_name`) are
stored in the encrypted session. When login returns no `merchant_id` and there are several
memberships, the picker is shown before the app; *Perfil → Cambiar de
comercio* opens it too. Choosing calls `POST /api/v1/auth/refresh
{refresh_token, merchant_id}` under the same single-flight lock as the 401
refresh; only a `401` ends the session (`403 NOT_A_MERCHANT_MEMBER`, 429 or
5xx keep the current one). Merchants are listed by `merchant_name` (the
business name the backend adds on login and refresh, `docs/AUTH.md`) with role
and id below; when the name is empty — the backend could not read the
merchant, or a session saved before batch M — the row falls back to
"Comercio <id>" until the next refresh brings the names.

### KYB onboarding (`ui/onboarding/`, `kyb/KybApi.kt`)

Contract: `GET|PUT /api/v1/merchants/{id}/kyb`, `POST .../kyb/documents`
(multipart `type` + `file`), `POST .../kyb/submit`. *Inicio* reads the KYB
status; while it is not `APPROVED` it shows the status card, disables *Nuevo
cobro* and opens the onboarding screen automatically once per app session (a
KYB `403` on a charge also links there). Flow for the owner: `DRAFT` → form
(client-side checks: RFC shape from `KybOnboardingPresenter`, CURP incl. the
state code, `tax_regime` as the backend enum — `RESICO_PF` preselected, the
only one that passes submission; `RESICO_PM`, `ACTIVIDAD_EMPRESARIAL_PF`,
`PLATAFORMAS_TECNOLOGICAS_PF`, `GENERAL_PM`, `OTHER` — MCC 4 digits, CP 5
digits, email, Mexican mobile → E.164 `+52…`, which matches the backend
`^\+[1-9][0-9]{7,14}$`) → `PUT` (`400 INVALID_KYB_DATA {fields}` marks those
fields) → documents → `submit` → status. The owner's GET carries
`application` and `uploaded_documents`: a resumed or rejected onboarding
prefills the form and counts stored documents as received. Each required
document (`required_documents`, always the six types today) is
captured with the camera intent (`TakePicture` into a FileProvider cache
file that is overwritten and deleted after reading), the system photo picker
(`PickVisualMedia`, no storage permission) or, for CSF / proof of address /
bank statement, a PDF (`GetContent`). Photos are decoded with
`ImageDecoder` (EXIF rotation applied), scaled to ≤ 2048 px and re-encoded as
JPEG 85 (drops EXIF/GPS); max 5 MiB per file (backend `MaxDocumentBytes`;
`413 DOCUMENT_TOO_LARGE` otherwise), upload answers `201`. Upload streams in 16 KiB chunks
with a progress bar; document bytes are zeroed after a successful upload, on
replacement and when the screen's ViewModel is cleared (a failed upload keeps
them for *Reintentar*; the PDF read buffer is zeroed on every exit path).
Submit answers `200` with `IN_REVIEW` (or `REJECTED` + `RFC_LISTED_69B`),
never `SUBMITTED` in practice; `422 KYB_CHECKS_FAILED` returns the KYB body
with status `DRAFT` and a check `reason` (`RFC_INVALID`,
`PERSONA_MORAL_NOT_SUPPORTED`, `UNSUPPORTED_TAX_REGIME`, `CURP_RFC_MISMATCH`,
`DOCUMENTS_INCOMPLETE`, `APPLICATION_INCOMPLETE`), shown translated on the
status screen with *Corregir*; `409 KYB_ALREADY_SUBMITTED` reloads the
status. `REJECTED` shows the operator's `reason` and lets the owner correct
and resubmit; `IN_REVIEW` only shows the status; cashiers/operators see the
status and "solo el dueño…" (no `application` in their response). The
backend never answers `404` for a merchant's KYB (it creates a `DRAFT` on
first read); the client still treats a bare `404` as "endpoint missing" and
disables the routing.

### CSD (`fiscal/CsdApi.kt`, `ui/fiscal/Csd*`)

*Perfil → Sellos digitales (CSD)*, owner only (hidden for other roles; the
backend enforces it too). `GET /api/v1/merchants/{id}/csd` →
`{serial, rfc, valid_from, valid_to, status:"ACTIVE"}` or `404 CSD_NOT_FOUND`;
the screen shows status, número de certificado, RFC, vigencia and warns when
fewer than 30 days remain (or it already expired). Upload: `.cer` and `.key`
picked with the SAF document picker (`OpenDocument`, no storage permission,
≤ 64 KiB, never copied to disk) and a masked password field →
`PUT .../csd` multipart `cer`, `key`, `password` → `200` same shape, or
`422 CSD_INVALID {reason}` (reason shown as sent). Client-side pre-checks
(`CsdInspector`, advisory): the certificate parses as X.509, is inside its
validity window, its holder RFC (x500UniqueIdentifier 2.5.4.45, "RFC / CURP")
equals the merchant's RFC, and the key looks like DER (PKCS#8, first byte
`0x30`); key decryption, pair matching and CSD-vs-FIEL are the backend's job.
The SAT serial is decoded from the ASCII-digit encoding. Sensitive data: the
password field uses plain `remember` (never saved instance state) and is
cleared on submit; the ViewModel receives a `CharArray`, the HTTP client
encodes it to a UTF-8 `ByteArray` without a `String`, and both are zeroed in
`finally`; the key bytes are zeroed after every attempt (a retry needs the key
picked again), on replacement and in `onCleared`. Nothing is logged.
(Compose `TextField` still holds the typed text as an immutable `String`
until the field is cleared — a platform limitation.)

### Invoicing (CFDI) (`fiscal/InvoiceApi.kt`, `ui/fiscal/Invoice*`)

- Entry points: *Facturar* on the detail of an approved (or partially
  refunded) sale, and *Seleccionar para facturar* in *Ventas* (checkboxes,
  only invoiceable sales; *Facturar seleccionadas (n)*). *Facturas* is
  reachable from *Ventas* and *Perfil*.
- Gate: the form reads `GET .../csd` on every visit; `404 CSD_NOT_FOUND` or a
  status other than `ACTIVE` (the backend sends `EXPIRED` for a stored
  certificate past `valid_to`) blocks it and links to the CSD screen (coming
  back re-checks). A create answering `422 CSD_NOT_FOUND` / `422 CSD_EXPIRED`
  does the same.
- Receptor form: RFC (upper-cased, SAT shape; 13 chars = persona física,
  12 = moral), nombre (as in the customer's CSF), régimen fiscal and uso CFDI
  from `GET /api/v1/catalogs/sat?names=regimen_fiscal,uso_cfdi`, filtered by
  `persona_fisica`/`persona_moral` and by the use's `regimenes`; changing the
  RFC or régimen drops choices that no longer fit. CP 5 digits, email
  optional. Catalogs live in memory (`SatCatalogCache`, one per process): fresh
  for 12 h, then refetched. The backend sends no `ETag` (only
  `Cache-Control: private, max-age=3600` and `X-SAT-Catalog-Version`), so no
  `If-None-Match` is sent; the `304` path stays only for a future ETag. A
  failed refresh serves the stale copy.
- `POST .../invoices {sale_ids, receptor[, replaces_invoice_id]}` with an
  `Idempotency-Key` stable per request body: kept on no response / unparsable
  / 5xx (the create's only 5xx is `503 INVOICES_UNAVAILABLE`), so *Reintentar*
  replays the same invoice; dropped on any 4xx or a result, and a new one
  when the receptor or sales change. A PAC outage is **not** a 5xx: it answers
  `201` with `status PENDING, error PAC_UNAVAILABLE` (the sales stay linked;
  the backoffice / worker retries). Mapped errors: `409 SALE_ALREADY_INVOICED
  {sale_id, invoice_id}` (the holder is fetched: a `kind GLOBAL` holder shows
  "ya está en la factura global"), `409 IDEMPOTENCY_KEY_REUSED`,
  `422 RECEPTOR_INVALID {fields: {field: reason}}` (an object; names with or
  without `receptor.` mark the fields), `422 FISCAL_PROFILE_INCOMPLETE
  {missing}`, `422 SALE_NOT_FOUND` / `SALE_NOT_INVOICEABLE`,
  `422 REPLACEMENT_INVALID`. The result screen shows `STAMPED` (UUID,
  total), `PENDING` ("se está timbrando") or `FAILED` (`error`, e.g. a SAT
  code like `CFDI40145`).
- *Facturas*: `GET .../invoices?limit=50&before=` with the same cursor rules
  as *Ventas*. Detail: `GET .../invoices/{id}` (kind, status, UUID, serie-folio
  — `folio` is a string —, subtotal/IVA/ISR retenido/total in Long cents with
  `total = subtotal + iva - isr_retenido`, receptor, dates, `global_period`
  for a factura global, and the `cancellation {motivo, status REQUESTED |
  ACCEPTED | REJECTED}`: a rejected request leaves the invoice `STAMPED` and
  is shown as such). *Compartir PDF/XML*
  downloads `GET .../{id}/pdf|xml` into `cache/invoices/` (emptied before each
  write, the download buffer is zeroed) and opens the share sheet with a
  content Uri of `InvoiceFileProvider` (authority `<appId>.invoicefiles`, not
  exported, read grant per Uri, paths file maps only `cache/invoices/`).
  Logout empties `cache/invoices/`.
- Cancel (owner, stamped only): motivos `01`–`03` for an individual invoice,
  `02`–`04` for a factura global (what the backend accepts) →
  `POST .../{id}/cancel`; `200 CANCELED` or `202 CANCEL_REQUESTED` (receptor
  has 72 h; the backend poller resolves it) replaces the shown invoice.
  Errors: `422 CANCEL_INVALID {fields}` (`REPLACEMENT_NOT_STAMPED` has its own
  message), `422 CANCEL_REJECTED`, `409 INVOICE_NOT_CANCELABLE` (reloads),
  `409 INVOICE_HAS_CREDIT_NOTES {credit_note_id}` (a live nota de crédito
  relates to the CFDI: "cancélalas primero" + *Ver nota de crédito*, which
  opens it to cancel it first; no reload),
  `502 PAC_UNAVAILABLE`, `403 ROLE_FORBIDDEN`. Cancel carries no
  Idempotency-Key: a repeat answers `409`, never a second PAC call.
- Motivo `01` (substitute): *Emitir factura sustituta* opens the form for the
  original's sales with its receptor prefilled; the create sends
  `replaces_invoice_id` (TipoRelacion 04, the substitute takes over the
  sales). Once it is `STAMPED`, *Cancelar la factura original* returns to the
  original with motivo `01` and `folio_sustitucion` = the substitute UUID.
- Sales already invoiced or in the factura global are greyed out beforehand
  (see *Sales*); the `409 SALE_ALREADY_INVOICED` mapping stays for a list
  that went stale.

(KYB GET/PUT/upload/submit incl. 400/409/422, card intent/payment/cancel/
refund, sales, the `403 MERCHANT_NOT_APPROVED` gate) were captured from the Go

handlers (batch J audit: `httptest` against `pkg/api` in memory mode with the
mock PAC — CSD PUT/GET incl. `WRONG_PASSWORD`, `MISSING_KEY`, `EXPIRED`,
`403`; invoice create `STAMPED`/`PENDING`/`FAILED`/substitute and every
error above; list pages; detail incl. global and rejected cancellation;
cancel `200`/`202`/`409`/`422`/`502`/`403`; catalogs) and exercised by
`contract/FiscalContractTest` (request method, path, query,
`Idempotency-Key`, multipart part names `cer`/`key`/`password` — the names
the handler reads —, JSON body keys, the motivo 01 flow).
Batch M (`sale_detail_*`, `sale_not_found_404.json`, `receipt_send_*`,
`sales_invoiced_page.json`, `invoice_cancel_has_credit_notes_409.json`,
`auth_refresh_memberships_200.json`, `auth_unauthorized_401.json`) are
written by `TestCaptureAndroidFixtures` (`pkg/api/android_fixtures_capture_test.go`,
skipped unless `ANDROID_FIXTURES_DIR` is set):
`ANDROID_FIXTURES_DIR=$PWD/mobile/android/app/src/test/resources/contract go test -count=1 -run TestCaptureAndroidFixtures ./pkg/api/`.
Token values in the token pair are replaced with placeholders; ids, receipt
tokens and timestamps change on every capture, so the tests read them from
the fixture instead of hard-coding them. `contract/ReceiptContractTest`
covers the sale detail and the receipt send.
`ui/fiscal/FileProviderHygieneTest` asserts both FileProviders are not
exported and that the invoice one maps only `cache/invoices/`. CSD tests use a
synthetic certificate built in memory (`fiscal/TestCertificates`): no `.cer`
or `.key` file is committed (both are git-ignored). Regenerate fixtures from
the backend tests when a response struct changes.

| `TapToPayProvider` | Debug: `MockTapToPayProvider` waits 1.5 s and calls `POST /api/v1/dev/card-payments/{id}/simulate {"outcome":"tap"}` (cancel → `"cancel"`), so a debug build against a `DEV_MODE` backend with the mock acquirer runs the real intent → webhook → ledger → polling path.
